Measuring our models' latency on a real NPU

The challenge measures latency on an XR edge-AI target, and the rules say "MACs are a proxy, not the score". On a desktop CPU, our TCN's latency followed the number of graph nodes (about 0.75 µs each) far more than its MACs. These two free services run an uploaded ONNX file on real hardware and report the inference time. Neither is an emulator.

Upload random-weight copies only. Latency doesn't depend on the weight values, so a copy with the same graph and random weights measures the same thing and keeps our trained models private.

1Make a random-weight copy of your ONNX file

This works for any exported model. It replaces every float weight tensor with random numbers of the same shape and spread. Integer tensors, such as Reshape shapes, are left alone.

import numpy as np, onnx
from onnx import numpy_helper

model = onnx.load("model.onnx")
rng = np.random.default_rng(0)
for t in model.graph.initializer:
    w = numpy_helper.to_array(t)
    if w.dtype == np.float32 and w.size > 16:
        noise = (rng.standard_normal(w.shape) * (w.std() or 0.05)).astype(np.float32)
        t.CopyFrom(numpy_helper.from_array(noise, t.name))
onnx.save(model, "model_random.onnx")

2Optional: an int8 copy

The STM32N6's NPU runs int8 models. Quantise the random copy yourself, so you don't upload any calibration data. Random calibration inputs are fine for timing, but they make the int8 file useless for accuracy.

import numpy as np, onnxruntime as ort
from onnxruntime.quantization import (CalibrationDataReader, QuantFormat,
                                      QuantType, quantize_static)

inputs = ort.InferenceSession("model_random.onnx").get_inputs()

class RandomInputs(CalibrationDataReader):
    def __init__(self): self.n = 0
    def get_next(self):
        self.n += 1
        if self.n > 32: return None
        rng = np.random.default_rng(self.n)
        return {i.name: rng.standard_normal([d if isinstance(d, int) else 1 for d in i.shape])
                          .astype(np.float32) for i in inputs}

quantize_static("model_random.onnx", "model_random_int8.onnx", RandomInputs(),
                quant_format=QuantFormat.QDQ, per_channel=True,
                activation_type=QuantType.QInt8, weight_type=QuantType.QInt8)

Keep 8-bit activations. 16-bit ones force ONNX opset 21, which ST probably doesn't accept yet.

3ST Edge AI Developer Cloud (ST does the official measuring)

  1. Create a free myST account and open ST Edge AI Developer Cloud.
  2. Upload the .onnx file. Uploads are private to your workspace.
  3. Choose the STM32N6 board, which has the Neural-ART NPU.
  4. Skip Quantize if you made your own int8 copy. Its quantiser wants your data, or calibrates on random numbers.
  5. Optimize, then Benchmark: the model runs on ST's hosted boards and you get the inference time, RAM and flash.
  6. Results compares runs side by side.

As far as we know, the NPU runs int8 only, so a float32 upload runs on the board's Cortex-M55 CPU. Comparing float with int8 there compares CPU with NPU.

4Qualcomm AI Hub (Snapdragon NPUs)

  1. Sign up at workbench.aihub.qualcomm.com. Your token is under Account, then Settings, then API Token.
  2. Install the client in a separate Python environment, then list the devices and look for an XR one. If there isn't one, a recent Snapdragon phone is the closest substitute.
pip install qai-hub
qai-hub configure --api_token YOUR_TOKEN
qai-hub list-devices
import qai_hub as hub

device = hub.Device("Samsung Galaxy S24 (Family)")   # pick one from list-devices
compiled = hub.submit_compile_job(model="model_random.onnx", device=device,
                                  options="--target_runtime qnn_dlc").get_target_model()
profile = hub.submit_profile_job(model=compiled, device=device).download_profile()
print(profile["execution_summary"])   # inference time is in here (microseconds)

Two details weren't confirmed in the docs we could reach: submit_profile_job (the getting-started page uses submit_inference_job(..., profile=True)) and the latency field's name. Check both with help(hub) the first time. Float models run in fp16 on the NPU.

5Snags to expect

  • A batch size other than 1 inside the graph. Microcontroller toolchains often assume batch 1. Our mirror model keeps its two streams in the batch axis, for example.
  • Many state inputs and outputs in a stateful graph. They should be supported, but it's untested on both services.
  • Unrolled recurrences longer than about 64 steps are on the challenge's avoid list. A stateless GRU that unrolls all 400 samples would hit this; a stateful one-step graph wouldn't.
